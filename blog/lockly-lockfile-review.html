Nobody reviews the lockfile. Introducing Lockly

A dependency bump changes three lines of package.json and four thousand lines of package-lock.json. GitHub collapses the second file by default, the reviewer approves the first, and whatever changed in the other 3,997 lines ships. That's where supply chain attacks live: an install script that wasn't there yesterday, a release from an account that has never published the package before, a version that's two days old. Lockly reads the part nobody reads.

What's worth stopping for

Most lockfile churn is noise, and a tool that flags everything gets ignored as quickly as the lockfile does. So Lockly lists every change but only raises the ones a reviewer should actually look at:

  • Install scripts: a package that now runs code when it's installed, the most common route for npm malware.
  • A new publisher: a release published by an account new to the package, or no longer through trusted publishing. That's what an account takeover looks like.
  • Lost provenance: the release before had a provenance attestation, this one doesn't.
  • Fresh releases and packages: a version published in the last few days, or a package that's only weeks old. Most malicious releases are caught and pulled within days, so a short wait is a cheap defence.
  • Changed contents or sources: the same version with a different hash, or a package suddenly coming from git, a URL or another registry.
  • Known vulnerabilities in the new versions, from OSV, and the ones the change fixes.
  • Deprecations, yanks and licence changes, including new copyleft terms.

It reads npm, Yarn (classic and Berry), pnpm, uv, Poetry, Pipenv, Go modules and Cargo lockfiles, and tells direct dependencies from transitive ones wherever the lockfile or its manifest says.

A flag isn't a verdict. It's the thirty seconds of checking you'd want before merging.

That's also why Lockly compares a release with the release just before it in the registry, not with whatever version you were on. If you jump three versions, a maintainer taking their turn in between isn't news; an account the package has never seen before is. Moving to trusted publishing is shown as information, since it's an improvement.

Pointing it at real repositories

Before release I ran it over the lockfile history of a few projects, mine and other people's:

  • Excalidraw, six months of yarn.lock changes: 4 packages added, 118 removed, 1 upgraded, and a single finding, the fsevents install script that macOS file watching has always needed. A well-run repository should look like this, and Lockly should stay quiet about it.
  • My VS Code extension, from its first lockfile to today: 34 upgrades fixed 10 known vulnerabilities and left 10 more in place, and 180 packages had switched to a private registry mirror. That one was deliberate, but it's exactly the kind of change a reviewer seeing it cold should ask about.
  • A small Vite app of mine: 58 packages added, and the vite version it locked had five advisories, one of them high, by the time I looked.

On every pull request

The point is to see this at review time, so Lockly ships as a GitHub Action. It compares the pull request with its base, posts the review as a single comment, and edits that comment on every push instead of adding new ones:

- uses: actions/checkout@v4
- uses: fullstackspectrum/lockly@v0
  with:
    fail-on: install-script,publisher,hash

--fail-on turns any finding type into a gate. Start with the ones that should never slip through unnoticed (a new install script, a new publisher, a changed hash) and tighten from there.

Where the data comes from

Lockly has no runtime dependencies. Everything it can tell from the lockfile alone, it does: hashes, sources, install scripts and licences where npm records them, and release dates where uv does. For the rest it looks up only the packages that changed in the npm registry, PyPI, crates.io, the Go module proxy and OSV, caches the answers for a day, and gives up on a slow request after five seconds. If a lookup fails, the review still runs and says what it couldn't check. --offline makes no requests at all.

Try it

pipx install lockly
brew install fullstackspectrum/lockly/lockly
docker run --rm -t -v "$PWD:/data" fullstackspectrum/lockly diff old/package-lock.json package-lock.json

Then, on any branch:

lockly diff --base origin/main
lockly diff --base origin/main --html report.html --markdown comment.md

It compares against the merge base, as a pull request does, and reads lockfiles you haven't committed yet.

Feedback

This is 0.1.0, and I'd rather tune the signals with real lockfiles than guess. If Lockly flags something that isn't worth a look, misses something that is, or can't read your lockfile, open an issue. Those are exactly the cases that make it better.
