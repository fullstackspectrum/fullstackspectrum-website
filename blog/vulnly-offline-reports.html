One report, any scanner: why Vulnly ships a single HTML file

You run a scanner against an image and get back a few thousand lines of JSON. Someone needs to make a call on it: the release manager, the auditor, the team lead who owns the service. That person usually isn't going to read raw JSON, and they shouldn't have to. Vulnly exists to close that gap. It takes scanner output and turns it into one HTML file that anyone can open.

The problem with scanner output

Trivy, Grype, Snyk and Cloudsmith all find vulnerabilities, but each one describes them differently. Severities sit under different keys, fix versions are nested in different places, and package identity is shaped differently each time. If you use more than one scanner, or switch between them, every dashboard or script you build ends up tied to a single format.

The usual fixes have their own costs. A hosted dashboard means another service to run and another place your vulnerability data lives. A spreadsheet export loses the context. A screenshot in a ticket goes out of date the moment someone asks a follow-up question.

One file, no network

The main design decision behind Vulnly is that the report is a single, self-contained HTML file. The fonts, the charting library and the logo are all embedded. Nothing comes from a CDN, and opening the report makes no outbound requests.

That turned out to matter more than I expected:

  • It works on airgapped hosts. Generate it in the restricted environment and open it there.
  • It archives cleanly. Attach it to a release, a ticket or an audit folder, and it will still render in two years because there's nothing external to break.
  • It's easy to share. It's a file, so you can email it, upload it as a CI artifact or drop it in Slack.

Vulnly itself follows the same idea. It has zero dependencies outside the Python standard library, so installing it doesn't pull in a tree of packages that you'd then need to scan.

From scan to report in one line

Install it from PyPI or Homebrew:

pip install vulnly
brew install fullstackspectrum/vulnly/vulnly

Then pipe any supported scanner straight in. Vulnly reads from stdin with - and detects the input format automatically:

trivy image -f json nginx:latest | vulnly -
grype nginx:latest -o json | vulnly -
snyk container test nginx:latest --json | vulnly -

If you want to be strict, for example in CI, pass --source. If the input doesn't match the source you named, Vulnly exits with a clear error instead of producing a misleading report:

vulnly scan.json --source trivy -o reports/nginx.html

What's in the report

The top of the report answers "how bad is it?" It shows severity counts, how many findings have a fix available, a distribution chart, and a short executive summary. The summary's alert tells you whether something is actually urgent, routine, or whether the scan came back clean. Those are three different conversations, and the report should say which one you're having.

Next is a top affected packages breakdown. In most scans, one or two dependencies account for most of the findings. Showing that early often points to the single upgrade that clears most of the list.

After that comes the full findings table, with search, severity filters, a fixable-only toggle, sortable columns and CSV export of whatever view you've filtered to. CVE and GHSA IDs link to NVD and GitHub Advisories.

The goal isn't to show every field the scanner returned. It's to help the reader decide what to fix first.

Cloudsmith users

If your packages live in Cloudsmith, Vulnly reads both the CLI's scan output and the v2 OSV vulnerabilities API. It also recognises repository-level summaries and turns them into an overview report covering every package in a repo:

cloudsmith vulnerabilities WORKSPACE/REPO/PACKAGE --output-format json | vulnly -

As with all the Cloudsmith tooling here, this is a community project and isn't affiliated with Cloudsmith.

Try it

Point it at an image you shipped this week and see what the report says. If your scanner's output doesn't parse, or you want a format I haven't covered, open an issue. Real-world JSON is what makes the parsers better.
