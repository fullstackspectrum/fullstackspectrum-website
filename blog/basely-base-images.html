Which base image should you use? Introducing Basely

Every Dockerfile starts with a decision most people make once and never revisit: the FROM line. Somebody picked python:3.12 two years ago because it was the first result, and it's been shipping 400 MB of compilers, headers and libraries into production ever since. Meanwhile there's a slim variant, an Alpine one, Docker Hardened Images, Chainguard images and a newer Python, and nobody has the afternoon it takes to compare them properly. Basely does that comparison for you.

Fewer CVEs isn't the whole answer

Comparing base images on vulnerability counts alone gives you the wrong answer surprisingly often. A distroless image with no shell will score brilliantly, then break the first RUN pip install in your build stage. An Alpine image swaps glibc for musl, and the native wheels your app depends on stop loading. Chainguard's free tier only tracks latest, which today means Python 3.15, not the 3.12 you asked for.

So Basely reads the Dockerfile as well as the images. A stage with RUN steps needs a shell, and if those steps call apt-get, it needs a Debian or Ubuntu base. The final stage, the one you ship, is better off with no shell or package manager at all. Every candidate gets a verdict for the stage it would replace:

  • drop-in: nothing in the stage should break.
  • minor changes: it works, but something differs: musl, a newer runtime, a non-root user, a missing platform.
  • needs changes: it would break the stage as written.

The recommendation is always the best image that won't break the stage. If something that needs more work at least halves the risk, Basely offers it as well, marked as worth the changes.

What it found

I pointed it at a typical two-stage Python Dockerfile: a python:3.12 build stage and a python:3.12-slim final stage. On the day I ran it, the full python:3.12 image carried 177 critical and high advisories in 412 MB. Its slim sibling had 29 in 43 MB. dhi.io/python:3.12, Docker's hardened image, had 7 in 23 MB, runs as a non-root user and ships no shell. Basely recommended that for the final stage, and its -dev variant for the build stage, so the two line up.

A few things surprised me while building it:

  • dhi.io/python:3.12-alpine had zero advisories in its OS packages, while the official python:3.12-alpine had 16, every one already fixed in Alpine. Same Alpine release, but one had picked up the new krb5 and zlib and the other hadn't been rebuilt yet.
  • node:22 looked like it had 657 advisories with fixes waiting. 615 of them were kernel advisories, pulled in through linux-libc-dev. A container runs on the host's kernel, so none of them apply. Basely leaves them out now.
  • The official Python images ship a pip with six CVEs of its own. It's easy to miss when you only count OS packages.
The best base image is the one with the fewest problems that still builds your app.

Where the numbers come from

Basely never pulls an image. It reads manifests and package databases straight from the registry, using your existing docker login, and streams each layer past without writing it to disk. Every package is looked up in OSV: OS packages against the distro's own advisory feed, so backported fixes count as fixed, and the language packages the image ships (pip, npm, Go modules, Maven JARs, gems) against theirs.

It also leaves out the noise. Advisories the distro marks as unimportant are dropped, along with kernel advisories, and so is anything a vendor has ruled out with VEX. Docker attaches OpenVEX statements to its hardened images, and Basely applies them: on dhi.io/python:3.12 that removed 49 advisories Docker had already assessed as not affecting the image. If your team keeps its own VEX, pass it with --vex.

Try it

Install it from PyPI or Homebrew, or run the container image:

pipx install basely
brew install fullstackspectrum/basely/basely
docker run --rm -t -v "$PWD:/data" fullstackspectrum/basely advise

Then run it next to a Dockerfile, or point it at an image or two:

basely advise
basely advise --image node:22
basely compare python:3.12 python:3.12-slim dhi.io/python:3.12

Each stage gets a comparison table and the recommendation as a FROM diff you can paste straight in. Like Vulnly and Sbomly, it also writes a self-contained HTML report that works offline, plus Markdown for a PR comment and JSON for other tools. Basely has no runtime dependencies and needs Python 3.10 or later; use 3.14 to read the zstd-compressed layers Docker Hardened Images use.

Keeping it honest in CI

--fail-on turns the advice into a gate. Fail when the shipped image runs as root, carries a critical advisory, or when Basely would recommend something better:

basely advise --fail-on root,critical,better

On GitHub it ships as a composite action that writes the advice to the job page:

- uses: fullstackspectrum/basely@v1
  with:
    dockerfile: Dockerfile
    fail-on: critical,root

Feedback

The catalogue covers Python, Node.js, Go and Java images, and Debian, Ubuntu and Alpine bases, from Docker Official Images, Docker Hardened Images and Chainguard. If your base image isn't covered, or Basely recommends something that breaks your build, open an issue with the Dockerfile. Those are exactly the cases that make the fit checks better.
