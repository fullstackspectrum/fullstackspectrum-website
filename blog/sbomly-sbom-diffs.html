What changed in this build? Introducing Sbomly

Most teams generate an SBOM for every build now. Fewer of them read one. The file gets attached to a release, maybe uploaded somewhere for compliance, and nobody looks at it again. The more useful question is never "what's in this build?" It's "what changed since the last one, and should I care?" Sbomly answers that question.

Why a plain diff isn't enough

You can diff two SBOM files with diff, but you'll regret it. Component order shifts between runs, generators add timestamps and serial numbers, and moving to a new base image changes the distro qualifier on every OS package. A raw diff shows hundreds of lines, and the one that matters is buried among them.

Sbomly pairs components across the two SBOMs by package URL, ignoring the version and the qualifiers that only describe the build environment. A new base image doesn't report every OS package as removed and re-added. What's left is a real list of components that were added, removed, upgraded or downgraded.

The changes worth stopping for

A version bump is usually routine. These four kinds of change usually aren't, so Sbomly lists them first:

  • Integrity: same version, different digest. The artifact was rebuilt or replaced, and you should know why.
  • Copyleft: a new dependency, or a new licence, that brings in GPL, LGPL, AGPL or similar.
  • Licence: a licence changed, or stopped being declared.
  • Supplier: a package's supplier changed. In a language ecosystem, that's what an account takeover looks like.

Some of these are expected, and Sbomly says so instead of raising an alarm. Distros rebuild unchanged packages for each release, so a digest change alongside a new distro qualifier is marked informational. The same goes for supplier changes on apk, deb and rpm packages, where the supplier is the distro maintainer and maintainers rotate.

Try it

Install it from PyPI or Homebrew, or run the container image:

pipx install sbomly
brew install fullstackspectrum/sbomly/sbomly
docker run --rm -t -v "$PWD:/data" fullstackspectrum/sbomly diff old.json new.json

Then compare two SBOMs. You can also read one from stdin, straight from a generator:

sbomly diff old.cdx.json new.cdx.json
syft my-image:latest -o cyclonedx-json | sbomly diff baseline.cdx.json -

The terminal summary lists findings first, most serious at the top, followed by each kind of component change. If you'd rather read changes the way you read code, -u prints a unified diff of the two component lists, one line per component, sorted like a lockfile.

Reports for wherever the review happens

Like Vulnly, Sbomly writes a self-contained HTML report with its fonts embedded. It opens offline, and search and filters still work, so you can attach it to a CI run or a ticket. It also writes a Markdown summary sized for a PR comment, and JSON for other tools:

sbomly diff old.json new.json --html report.html --markdown pr.md --json diff.json

Sbomly itself has no runtime dependencies. It needs Python 3.10 or later and nothing else.

Gating CI

--fail-on turns any category into a build gate. A sensible starting point is to fail on rebuilt artifacts, new copyleft and downgrades:

sbomly diff main.cdx.json pr.cdx.json --fail-on hash,copyleft,downgraded

On GitHub, Sbomly also ships as a composite action that writes the Markdown summary to the job page:

- uses: fullstackspectrum/sbomly@v0.1.0
  with:
    old: sbom-main.cdx.json
    new: sbom-pr.cdx.json
    fail-on: hash,copyleft
An SBOM on its own is an inventory. Two SBOMs compared side by side tell you what to review.

Feedback

SBOM generators disagree on a lot of details, and real files are what improve the matching. If Sbomly reports noise it shouldn't, or misses a change it should catch, open an issue, ideally with the two SBOMs attached.
